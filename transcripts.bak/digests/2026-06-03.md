### Why AI evals are the hottest new skill for product builders | Hamel Husain & Shreya Shankar (creators of the #1 eval course)

**Summary**

The episode establishes that mastering AI evaluations ("Evals") is currently the highest ROI skill for product builders working with LLMs, moving it from an obscure topic to a critical industry necessity. Evals are defined as systematic methods to measure and improve AI applications, providing data-driven metrics that replace unreliable "vibe checks" and guesswork in complex, stochastic systems. The discussion emphasizes that while unit tests check non-negotiable functionalities, true evals require deep data analysis to assess performance across ambiguous tasks, new user cohorts, and overall product quality over time.

The guests, Hamil Hussain and Shreya Shankar, are positioned as definitive authorities on the subject. They have played a major role in popularizing Evals, having taught thousands of PMs and engineers across major AI labs (including OpenAI and Anthropic). Their background provides credibility by offering practical frameworks to demystify the process, moving it from an intimidating technical challenge into a manageable product development cycle.

**Key Points**

- **Evals are not just tests:** The common misconception is that Evals are simply writing unit tests for code. In reality, they start with *data analysis* to ground what should be tested, especially because LLMs operate in a highly stochastic (non-linear) environment.
- **The scope of Evals is vast:** Beyond checking specific functions (like booking an appointment), evals must measure ambiguous performance—such as how well the AI handles new types of user requests or identifies entirely new user cohorts that were not anticipated during development.
- **Avoid "Committee Paralysis":** When building evals, do not let a committee make the decision; this process can become prohibitively expensive and slow. Instead, appoint one person with deep domain expertise (often the Product Manager) to act as the trusted authority ("benevolent dictator").
- **The Goal is Actionable Improvement:** The purpose of running an eval is not perfection or achieving perfect scores; it is to generate a clear feedback signal that allows the team to iterate and improve the product with confidence.
- **Unit Tests vs. Evals:** Unit tests are ideal for checking non-negotiable, core functionalities. Evals encompass this but also include tracking metrics over time (e.g., user satisfaction scores like "thumbs up") and analyzing data distributions to find new opportunities.

**Action Items**

- [ ] **Skill Development:** Dedicate time to learning the methodology of AI Evals, focusing on systematic measurement rather than just prompt engineering. (Recommended resource: Hamil & Shreya’s course on Maven).
- [ ] **Product Strategy:** When building an AI product, prioritize conducting preliminary data analysis *before* writing any tests or defining metrics. Use existing user interaction logs to define the scope of your evaluation.
- [ ] **Team Structure:** Establish a single point of domain expertise (e.g., the PM) responsible for setting and trusting the core evaluation criteria, preventing decision paralysis from large committees.
- [ ] **Tool Implementation:** If managing customer support or product research, evaluate using specialized tools like Finn AI (for high resolution rates) or D-Scout (for streamlined user testing/fieldwork).

### The secret to better AI prototypes: Why Tinder’s CPO starts with JSON, not design | Ravi Mehta (product advisor, previously EIR at Reforge)

**Summary**

The episode challenges traditional product development assumptions that rely on design systems or visual mockups as the foundation for AI prototyping. Ravi Mehta, a seasoned product leader who previously served as CPO at Tinder and worked with major companies like Facebook and TripAdvisor, argues that true efficiency comes from shifting focus to **data structure**. He introduces "data-driven prototyping," a methodology where the prompt is built around defining a concrete data schema (using JSON) rather than describing the desired UI or aesthetic.

The core discussion revolves around moving beyond "vibe coding" or vague prompts—such as "make it look nice"—which often result in average, unoptimized prototypes. Instead, by providing structured input that mimics how engineers think (i.e., defining the data model first), users can force AI tools to generate highly functional, componentized code and mock data sets, effectively accelerating the product development lifecycle from concept to a testable structure.

**Key Points**

- **Data Schema > Design:** The foundation of great prototyping should be the underlying data model (JSON schema), not the visual design or UX description. This approach forces the AI to think like an engineer first, making the resulting prototype more functional and flexible for testing different data sets.
- **The Failure of Vague Prompts:** Generic prompts ("make a website for planning a Paris trip") lead to outputs that are "average across those things" because the AI is trying to optimize for design, product, *and* engineering simultaneously without clear constraints.
- **Data-Driven Workflow:** The optimal method involves defining the data structure first: *"Generate a sample itinerary... using JSON."* This approach forces the tool to create not only the UI components but also the necessary underlying mock data (`libmock.ts`), which is crucial for accurate user feedback testing.
- **Accelerated Product Development:** Data-driven prompting acts as an accelerated version of the traditional product development process, allowing PMs and designers to rapidly iterate on complex features (like multi-user trip planning) by focusing on functionality and data constraints rather than visual polish.

**Action Items**

- [ ] **Master Structured Prompting:** When using any generative AI tool (LLMs, image generators), shift your prompts from descriptive language ("make it look nice") to structured data requirements (e.g., "Using JSON format, generate a schema for X...").
- [ ] **Define the Data Schema First:** Before prototyping a feature, force yourself to write out the required data fields and relationships in a JSON or YAML structure. Use this schema as the primary input prompt for AI tools.
- [ ] **Test Data Integrity:** When reviewing AI prototypes, specifically look for hallucinations (e.g., broken URLs, incorrect geographic locations) and treat them as immediate failure points that require manual correction/refinement of the prompt.
- [ ] **Explore Reforge Build:** If you are in a product role, investigate tools like Reforge Build to see how they handle structured data inputs versus simple text prompts for prototyping established products.

**Key Points**

- **Autonomous Debugging:** Modern AI agents can perform complex tasks (e.g., fixing lint errors) by autonomously executing terminal commands (`bun run lint`), diagnosing issues, applying code changes, and then re-running the command to verify success. ### Episode 270: How Experimentation Becomes Culture

**Summary**

The episode explores how to transition experimentation from an abstract concept or a mandatory "check-the-box" exercise into a deeply embedded, sticky organizational culture. The discussion moves beyond theory, focusing on specific leadership behaviors, portfolio management strategies, and systemic changes required for continuous learning within product organizations. Three experts—David Bland, Monica Lewis, and Mario Rodriguez—provide complementary insights: Bland addresses the mindset shift needed to treat experimentation as de-risking rather than just a feature checklist; Lewis details how leaders must actively build psychological safety through vulnerability and process transparency; and Rodriguez illustrates the outcome of this culture by discussing the high-velocity failure and iteration that built Copilot. The core thesis is that sustained experimental capability requires constant, visible effort from leadership to prevent teams from reverting to comfortable, established processes.

**Key Points**

- **The Danger of "Theater" Experimentation:** If experimentation is merely an added step on the path to shipping a product already decided upon, it fails and becomes organizational theater. True experimentation must focus on de-risking high uncertainty areas, not just optimizing known paths.
- **The Bloodstream vs. DNA Principle (Leadership Modeling):** Organizational processes can become ingrained in "bloodstream" (a functional habit) but are not truly part of the company's "DNA." As soon as leadership stops talking about and modeling experimental behavior, teams will revert to their previous, comfortable working methods, requiring a constant effort to restart the cultural program.
- **Building Psychological Safety Through Vulnerability:** Leaders must actively model failure to encourage team testing. Specific actions include: 1) Owning mistakes publicly (e.g., in an all-hands meeting). 2) Sharing "skeleton documents" or unfinished thinking early, inviting feedback before clarity is achieved. This shifts the culture from seeking final answers to valuing input on incomplete ideas.
- **Strategic Portfolio Allocation Framework:** When allocating resources for testing and bets, organizations should categorize investments into three buckets: **Sure Bets** (known payoffs), **Strategic/Unknowns**, and **Venture Bets** (high risk/high reward). A common starting allocation model is 60% / 30% / 10%, though this ratio must be adjusted based on the current level of business disruption.
- **The Acceptance Rate Fallacy:** High adoption does not require a high initial acceptance rate for suggestions. Mario Rodriguez notes that even if only 20–30% of users accept a suggestion, if those who adopt it find immense value, the product is successful. Focus on the *value* delivered to early adopters, not just the raw percentage of clicks or approvals.

**Action Items**

- [ ] **Implement Public Failure:** Commit to publicly owning a mistake or admitting when your initial hypothesis was wrong during a team meeting (e.g., "I was wrong about X because..."). This models vulnerability and increases psychological safety for others.
- [ ] **Pre-Mortem/Skeleton Sharing:** Before finalizing any major plan, circulate an early draft ("skeleton doc") to the team with the explicit instruction: "What is wrong with this?" or "How does this change things?" This forces discovery research *before* the roadmap is locked down.
- [ ] **Audit Portfolio Bets:** Review your current product investment portfolio and formally categorize each initiative into Sure Bet, Strategic Unknown, and Venture Bet. Adjust resource allocation to reflect the current level of market disruption (e.g., increase venture bets if the industry feels volatile).
- [ ] **Model Repetition:** Recognize that cultural change is not a one-time training session. If you want experimentation to stick, leadership must constantly repeat, evangelize, and model the desired behavior until it becomes routine.

### The Real Problem With AI Agents Nobody's Talking About

**Summary**

The episode argues that the current hype surrounding AI agents is fundamentally misunderstanding the core challenge of implementation. While installing an agent is trivial—a process solved in seconds—the massive gap lies between mere installation and achieving genuine, measurable productivity. The speaker critiques the "OpenClaw Me Too" landscape, noting that most products fail because they address the symptom (lack of access) rather than the root cause: the difficulty for humans to articulate complex intent to a machine.

The central thesis is that agents are not inherently magical; their utility depends entirely on robust, structured context. Success does not come from advanced AI models alone, but from treating the agent's configuration files as its "operating system." The speaker outlines a proven architecture involving specialized roles, clear boundaries, and dedicated memory management to move beyond generic, useless deployments toward true operational value.

**Key Points**

- **The Productivity Gap:** There is a massive disconnect between the ease of *installing* an agent (which everyone has solved) and the difficulty of making it *productively useful*. Simply having an agent does not guarantee 10X ROI.
- **Failure Mode: Generic Agents are Liabilities:** A generic agent with access to sensitive data (like email) is worse than no agent at all; it represents a liability because its lack of defined purpose leads to unusable, unguided output.
- **The Successful Architecture Pattern:** Working multi-agent systems do not rely on one "do-everything bot." They function like a team with clear separation of concerns. This architecture requires specific plain text files that define the agent's operational parameters:
    *   `role.markdown`: Defines the job, tone, and boundaries (the job description).
    *   `identity.markdown`: Sets the name and personality constraints.
    *   `user.markdown`: Provides a detailed profile of the human user (preferences, schedule patterns).
    *   `heartbeat.markdown`: A mandatory checklist that forces the agent to review its status every set interval to determine if action is needed.
- **Specialization over Generalism:** The most effective setups use multiple specialized agents (e.g., a Marketing Manager Agent, a Scheduler Agent) that have clear jurisdictions and do not share context with each other, mimicking human co-workers.
- **The Necessity of Memory/Intent:** For an agent to be smart, it must learn and improve over time. Successful implementations require dedicated memory management—either through accumulating insights in a `memory.markdown` file or, ideally, connecting the agent to a searchable database (like OpenBrain approaches) for richer, multidimensional context retrieval.
- **The Human Input Requirement:** The ultimate bottleneck is human clarity of intent. To get an agent to perform successfully, the human must sit down and describe in highly detailed, verifiable language exactly what they do all day.

**Action Items**

- [ ] **Audit Current Agent Use:** Identify one area in your business where you currently use an AI agent or automation tool, and determine if its failure point is *installation* (easy) or *context/intent* (hard).
- [ ] **Implement Role Separation:** Instead of using a single "super agent," map out 2-3 specialized roles within your workflow (e.g., Research Agent, Drafting Agent, Review Agent). Treat each role as a separate entity with its own defined boundaries and purpose.
- [ ] **Build the Operating System:** For your primary agent, create or refine the four core markdown files (`role`, `identity`, `user`, `heartbeat`). Focus on making these definitions highly specific, verifiable, and actionable—this is the most critical step for increasing ROI.
- [ ] **Establish Memory Protocol:** If you are building an advanced system, move beyond simple chat history. Implement a dedicated knowledge base or database that your agents must query before generating output to ensure continuity and learning over time.
